# 费用报销模块 —— 差旅与业务招待费报销智能体

> 本模块为 `箱包制造企业采购与库存管理系统` 的功能扩展，实现「填单上传 → AI 识别 → 人工确认 → AI 判读 → AI 制证 → 确认凭证 → 凭证复核」的完整费用报销流程。
>
> 设计依据：《信息系统审计 实验一 差旅与业务招待费报销智能体的设计与开发》
> 判读依据：《星辰科技股份有限公司 差旅与业务招待费报销管理制度》XC-CW-2025-008

---

## 一、功能概览

| 环节 | 执行者 | 主要工作 | 程序校验 / 人工控制 |
|---|---|---|---|
| ① 填写报销单 | 报销人 | 填报销人、费用类型、发生日期、审批人（下拉选择有审批权限的人员，自动带出审批层级），以及差旅/招待专项信息，上传票据；报销事由可点「AI 生成报销事由」按票据与已填信息生成 | 基础必填校验；报销日期与单号由系统生成 |
| ② 票据识别 | **大模型** | 提取票据类型、号码、金额、税额、日期、乘车人、入住离店、城市等，并给出费用类型建议；识别完成后自动回填费用类型与差旅专项（出差地点 / 出差起止日期 / 住宿晚数，已手工填写的字段不覆盖，费用类型已选时给出「采用」按钮）；支持图片与 **PDF**（见 9.2 节双路径策略） | 金额勾稽、大写金额、日期格式等程序校验 |
| ③ 信息确认 | 报销人 | 对照原件核对、修改识别结果 | 人工修改留痕；发票号码唯一性校验 |
| ④ 合规判读 | **程序 + 大模型** | 程序先算星期/节假日/人均/每晚金额/关联单；大模型读制度逐条判读 | 程序交叉校验；总体结论由程序汇总；不合规禁止制证 |
| ⑤ AI 制证 | **大模型** | 生成分录、进项税额处理、会计处理说明 | 借贷平衡、科目有效、金额一致、税务规则校验 |
| ⑥ 确认凭证 | 制单员 | 检查修改 AI 凭证后确认保存 | 修改留痕；制单人不能是报销人 |
| ⑦ 凭证复核 | 复核员 | 对照判读结论、凭证、票据复核 | 复核人不能是制单人或报销人 |

## 二、核心设计：「AI 做判断，程序做校验，人做决定」

大模型承担三类任务：票据识别、合规判读、凭证生成。判断越多出错影响越大，因此每一项 AI 输出都要经程序校验并由人确认后才能产生正式业务结果。

### 2.1 判读流程四阶段

1. **事实计算（纯程序）**：大模型不擅长精确日期推算与数值计算，也不能查数据库历史报销单。星期、节假日、人均金额、每晚金额、关联报销单等事实全部由程序算出后提供给 AI。
2. **AI 判读（大模型）**：把制度正文、14 条检查规则、报销信息、票据信息、程序事实一起交给 qwen-plus，逐条给出结论、理由、整改提示。
3. **交叉校验与汇总（程序）**：程序对 9 项量化规则独立判断触发条件，与 AI 结论比对标出不一致项；补全 AI 漏判的规则；**总体结论由程序汇总，AI 自评结论只作记录**。
4. **结果处理（人）**：报销人整改或补充说明；必要时由制单员/管理员人工覆盖并留痕。

### 2.2 14 项检查规则

| 编号 | 检查项 | 条款 | 风险 | 方式 |
|---|---|---|---|---|
| R01 | 审批权限是否匹配 | 第四条 | 高 | AI+程序 |
| R02 | 是否拆分报销 | 第五条 | 高 | AI+程序 |
| R03 | 招待人均是否超标 | 第七条① | 中 | AI+程序 |
| R04 | 招待单次是否超标 | 第七条② | 中 | AI+程序 |
| R05 | 是否周末/节假日招待 | 第八条 | 中 | AI+程序 |
| R06 | 住宿是否超标 | 第九条 | 中 | AI+程序 |
| R07 | 是否缺发票 | 第十一条 | 高 | AI+程序 |
| R08 | 是否跨期报销 | 第十二条 | 中 | AI+程序 |
| R09 | 是否疑似重复 | 第三条 | 高 | AI+程序 |
| R10 | 招待要素是否齐全 | 第六条 | 中 | AI |
| R11 | 差旅要素是否齐全 | 第十条 | 中 | AI |
| R12 | 单据要素是否齐全 | 第十三条 | 低 | AI |
| R13 | 票据与填报是否一致 | 第三条、第十一条 | 高 | AI |
| R14 | 报销事由是否合理 | 第三条 | 中 | AI |

R01～R09 程序也能独立判断触发条件，用于与 AI 结论交叉校验；R10～R14 需要理解文字含义，只能由大模型判断。

## 三、应用控制设计

| 控制目标 | 系统控制措施 | 实现位置 |
|---|---|---|
| 输入真实准确 | 识别结果须人工确认后入库；保存 AI 原始识别结果 | `rmb_invoice.llm_raw_json` |
| 防止重复报销 | 发票号码唯一索引；票据文件哈希比对；同人同额同类型同日检查 | `rmb_invoice` 唯一约束、R09 规则 |
| 制度得到执行 | 14 项规则逐条判读；判读不合规禁止制证 | `compliance_ai.py`、报销单状态 |
| AI 判读可靠 | 事实由程序计算；程序对 9 项规则交叉校验；AI 漏判自动补为「需关注」；总体结论程序汇总 | `fact_service.py`、`compliance_ai.py` |
| 防范提示词注入 | 用户填写内容作为数据隔离并声明指令不得执行；程序交叉校验兜底 | `compliance_ai.py`、`voucher_ai.py` |
| 人工覆盖受控 | 仅制单员/管理员可覆盖，不得是报销人本人；理由必填并留痕；复核时醒目提示，不能批量复核 | 判读结果页、复核页 |
| AI 凭证正确 | 借贷平衡；末级启用科目；借方合计=报销金额；贷方=结算科目；业务招待费不得抵扣进项 | `voucher_ai.validate_voucher()` |
| 凭证编号连续 | 凭证号由程序在事务中生成，大模型不参与编号 | `vouchers.py` |
| 职责分离 | 报销人/制单人/复核人三者分离；角色权限控制 | `role_required`、制证与复核接口 |
| 制度变更受控 | 制度、规则、阈值参数只能管理员改，改前后值写日志 | 制度管理页、操作日志 |
| 审计轨迹可追溯 | 全流程写日志，含 AI 模型、耗时、结论、不一致项数 | `operation_logs.detail` |
| 信息安全 | API Key 存 `.env` 不提交；SQL 全参数化；限制上传类型与大小 | `config.py`、`.gitignore` |

### 4.2 数据库表（16 张）

**基础表**：`rmb_department`、`rmb_employee`、`rmb_account_subject`、`rmb_expense_type`、`rmb_settlement_method`、`rmb_city_level`、`rmb_holiday`、`rmb_sys_param`、`rmb_policy`、`rmb_policy_rule`

**审计表**：复用系统已有的 `operation_logs`（已补充 `detail` 字段记录业务明细）

关键约束：
- `rmb_invoice.invoice_number` UNIQUE —— 有号码的发票不得重复使用
- `rmb_voucher.reimbursement_id` UNIQUE —— 一张报销单只生成一张凭证
- `rmb_voucher(period, voucher_word, voucher_no)` UNIQUE —— 凭证号不重号

### 4.4 会计处理要点（AI 制证依据）

| 业务情形 | 借方 | 进项税额处理 |
|---|---|---|
| 差旅住宿费，取得增值税专用发票 | 管理费用—差旅费（不含税）+ 进项税额（票面税额） | 按票面税额抵扣 |
| 差旅住宿费，取得普通发票 | 管理费用—差旅费（价税合计） | 不得抵扣 |
| 差旅交通费，火车票/机票行程单 | 管理费用—差旅费（扣除计算抵扣额后）+ 进项税额 | 铁路航空按 票面÷(1+9%)×9%；公路水路 ÷(1+3%)×3% |
| 业务招待费（任何票据） | 管理费用—业务招待费（价税合计） | **不得抵扣** |
| 无发票但经特批/人工覆盖 | 对应费用科目（全额） | 不得抵扣 |
| 跨期费用 | 按上述规则处理，摘要注明发生期间 | 提示按权责发生制归属期间 |

贷方科目统一取报销单所选结算方式的对应科目：银行转账→1002 银行存款、现金支付→1001 库存现金、挂账→224101 其他应付款。

## 五、快速开始

### 5.1 初始化（首次运行）

```powershell
cd backend

# 1. 建表 + 基础数据（科目/费用类型/城市/节假日/参数/14条规则/部门员工）
.\.venv\Scripts\python.exe scripts\upgrade_db_v6_reimburse.py

# 2. 导入制度正文（AI 判读依据）
.\.venv\Scripts\python.exe scripts\import_policy_text.py

# 3. 关联用户与员工档案，创建制单员/复核员角色
.\.venv\Scripts\python.exe scripts\link_reimburse_users.py
```

### 5.2 启动

```powershell
# 后端（必须从 backend 目录启动）
cd backend
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 前端（另开终端）
cd frontend
node_modules\.bin\vite
```

访问 `http://127.0.0.1:5173/#/reimburse/list`，用下方账号登录。

### 5.4 分级审批（制度第四条）

制度要求按单笔报销金额分级审批，系统据此建立 4 个审批角色：

| 单笔金额 | 审批层级 | 角色 | 演示账号 |
|---|---|---|---|
| 低于 5,000 元 | 1 级 | 部门负责人 / 财务复核 | `depthead` / `manager` |
| 5,000（含）～ 20,000 元 | 2 级 | 部门总监 | `director` |
| 20,000（含）元以上 | 3 级 | 总经理 | `gm` |

**审批规则**：

1. **向上兼容**：层级高的人可审批低层级单据（总经理当然能批 3,000 元的单），
   但层级低的人不能越权（部门负责人批不了 8,500 元的单）。
2. **自审防范**：报销人不能审批自己提交的单据，与制单、复核的职责分离要求一致。
3. **意见留痕**：驳回必须填原因；二级以上审批（5,000 元以上）无论通过与否都须填意见。
4. **状态联动**：驳回后单据退回「待判读」，报销人修改后可重新提交。
5. **作废受审批结果约束**：单据一旦审批通过，**报销人本人不能再自行作废**，
   须由具备「报销单-作废」（`reimburse:bill:delete`）权限的管理岗操作并留痕；
   已生成凭证的单据任何角色都不允许作废。未审批的单据，报销人仍可自行作废本人单据。

**审批与判读是两条独立的控制线**：

- **审批**（`approval_status`）管「谁有权批这张单」——制度第四条的授权控制；
- **判读**（`compliance_result`）管「这张单符不符合制度标准」——R01～R14 的合规控制。

两者互不替代，共同构成报销的准入条件。

**接口**：`POST /api/v1/rmb-bills/{id}/approve`，参数 `{action: 'approve'|'reject', comment}`，
权限码 `reimburse:bill:approve`。前端在报销单详情页右上角「审批」按钮，列表页有「审批」状态列。

**验证脚本**：`scripts/verify_approval_roles.py`（15 项检查，覆盖层级计算、越权拦截、向上兼容、自审防范）。

### 5.6 财务岗的职责分离修正

原先 `manager`（陈静）同时持有**制单**与**凭证复核**两项权限 —— 同一个人既能制证
又能复核，违反职责分离。现已按岗位职责拆分：

| 岗位 | 账号 | 能做 | **不能做** |
|---|---|---|---|
| 财务复核（管理） | `manager` 陈静 | 填单、审批、判读、覆盖 | **制单、复核凭证** |
| 财务制单 | `finmaker` 吴强 | 审批、判读、覆盖、**制证** | **复核凭证** |
| 财务复核（执行） | `finance` 周敏 | 审批、判读、覆盖、**复核凭证** | **制单** |

三人**都可审批**（制度第四条允许财务复核审 <5,000 元），但制单与复核严格互斥。

**实现方式**：用**用户级权限覆盖**（`user_permissions`，effect=deny）禁用陈静的
`voucher:make` / `voucher:review`，不动 `manager` 角色本身（该角色还承载采购/库存/
报表等 30 项业务权限）。系统判定顺序是「用户级 deny 优先于一切（含 admin 放行）」，
因此能可靠生效，且在**用户管理 → 配置权限**页面可以看到这两项被取消勾选。

**验证脚本**：`scripts/align_permissions_by_dept_position.py`
（幂等；会输出完整矩阵并校验全局是否还有「制单+复核」共存的账号）

### 5.7 数据范围（部门 × 职位）

权限码只解决「**能不能**做某个动作」，数据范围解决「**能对哪些单据**做」。
制度第四条的分级审批是按部门层层上报的：部门负责人只对本部门单据负责，
财务复核与总经理则对公司整体负责。

| 职位（角色） | 数据范围 | 说明 |
|---|---|---|
| 部门负责人 `dept_head` | **本部门** | 只审批本部门单据 |
| 部门总监 `dept_director` | **本部门** | 只审批本部门单据 |
| 财务复核 `finance_review` | 全公司 | 财务是职能条线，跨部门 |
| 财务审批 `finance_approve` | 全公司 | 同上 |
| 总经理 `general_manager` | 全公司 | 经营全局 |
| 制单员 `maker` / 复核员 `reviewer` | 全公司 | 为全公司制证、复核 |
| 系统管理员 `admin` / 运营主管 `manager` | 全公司 | 管理职能 |
| 普通员工 `staff` / 采购员 / 仓管员 / 质检员 | **仅本人** | 只看自己的报销单 |

**实现要点**：

1. `ROLE_DATA_SCOPE` 定义角色到范围的映射，一人多岗时取最高档（all > dept > self）。
2. 部门管理岗若**没有员工档案**（无法判断所属部门），自动降级为 `self` —— 宁可少看，不可越权。
3. 单据的部门取 `bill.department_id`，缺失时回退到报销人的员工档案部门。
4. 三条独立的控制线共同决定一次审批是否成立：

```
① 权限码   reimburse:bill:approve     → 能不能审批
② 数据范围 bill_in_scope()            → 能审哪些单据（本部门 / 全公司）
③ 审批层级 user_approval_rank()       → 能审多大金额（1/2/3 级）
   外加：报销人不得审批自己的单据
```

**可见范围的实际表现**（当前 10 张演示单）：

| 账号 | 数据范围 | 可见单据 |
|---|---|---|
| `admin` / `gm` / `finance` / `finmaker` / `maker` / `reviewer` | 全公司 | 10 张 |
| `depthead` / `director`（销售部） | 本部门 | 5 张（全是销售部） |
| `sales`（郑洁，无报销单） | 仅本人 | 0 张 |
| `buyer`（王五） | 仅本人 | 5 张（全是本人） |

**验证脚本**：`scripts/verify_data_scope.py`（14 项检查，覆盖可见数量、跨部门审批拦截、
同部门审批放行、全公司范围跨部门审批、跨部门详情不可见）。

## 九之二、PDF 票据识别

票据识别支持 **PDF / JPG / JPEG / PNG** 四种格式。PDF 采用**双路径**策略，由程序自动判断：

| 路径 | 适用情形 | 处理方式 | 使用模型 |
|---|---|---|---|
| **PDF 文本解析** | 电子发票类 PDF（文字可选中） | `pypdf` 提取文本层 → 文本模型解析 | `qwen-plus` |
| **PDF 渲染识别** | 扫描件 PDF（图片压入，无文本层） | `pypdfium2` 将首页渲染为 PNG → 视觉模型识别 | `qwen3-vl-plus` |

**为什么优先走文本**：电子发票的文字本身就在 PDF 里，直接抽出来比截图识别更准确（不受压缩、倾斜、分辨率影响），耗时更短（约 9 秒 vs 10 秒），token 消耗也低得多。

判定规则：抽取的文本去空白后 ≥ 30 字视为「有文本层」，否则自动降级为渲染路径。

### 依赖说明

```
pypdf==5.1.0        # 纯 Python，提取文本型 PDF 的文字
pypdfium2==4.30.0   # 自带预编译二进制，渲染扫描件 PDF；不需要外部 poppler
```

### 大小限制

| 类型 | 识别上限 | 归档上限 |
|---|---|---|
| 图片（jpg/jpeg/png） | 8MB | 20MB |
| PDF | 20MB | 20MB |

> 归档上限统一为 20MB：否则会出现「能保存但识别必失败」的割裂体验。

### 识别模式留痕

接口响应与审计日志都会记录 `recognize_mode`：

| 取值 | 含义 |
|---|---|
| `image` | 图片走视觉模型 |
| `pdf_text` | PDF 文本层 → 文本模型 |
| `pdf_render` | PDF 扫描件渲染 → 视觉模型 |

审计日志示例（`operation_logs.detail`）：

```
住宿费专票_文本型.pdf；PDF文本解析；模型qwen-plus；耗时9.1s；成功
```
